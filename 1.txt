1. برای مقیاس‌پذیری، API را به بخش‌های جدا مثل route، controller و service تقسیم می‌کنم.

سرویس را stateless نگه می‌دارم و از cache، pagination و connection pool استفاده می‌کنم.

برای ترافیک بالا هم چند instance با Docker و Load Balancer اجرا می‌کنم.

2. یک middleware مرکزی برای مدیریت خطاها می‌نویسم تا همه خطاها یک شکل برگردند.

در محیط اصلی، جزئیات خطای داخلی را به کاربر نشان نمی‌دهم.

خطاها با شناسه درخواست در لاگ ثبت می‌شوند تا عیب‌یابی راحت تر شود.

3. ورودی‌ها را با ابزارهایی مثل Joi، Zod یا express-validator بررسی می‌کنم.

نوع داده، طول، فرمت و اجباری بودن فیلدها باید کنترل شود.

برای جلوگیری از حمله هم ورودی‌ها باید پاک سازی و محدود شوند.

4. اول با لاگ‌ها، APM و ابزارهایی مثل Clinic.js یا Node Profiler پیدا می‌کنم مشکل از کجاست.

زمان کوئری دیتابیس، درخواست‌های خارجی، CPU و memory را بررسی می‌کنم.

بعد با cache، index، pagination و بهینه کردن کد سرعت را بهتر می‌کنم.

5. روی endpoint ورود rate limit می‌گذارم و تعداد تلاش‌های ناموفق را محدود می‌کنم.

بعد از چند تلاش، تاخیر، قفل موقت حساب یا CAPTCHA فعال می‌شود.

رمزها هم باید با bcrypt یا Argon2 هش شوند و تلاش‌های مشکوک لاگ شوند.

6. وقتی چند نوع کلاینت اطلاعات متفاوتی لازم دارند، GraphQL میتواند مناسب‌تر باشد.

این کار مشکل دریافت اطلاعات اضافی یا کم را کمتر می‌کند.

ولی برای APIهای ساده و قابل cache، معمولاً REST انتخاب راحت‌تری است.

7. مسیر فایل را مستقیم از کاربر قبول نمی‌کنم و فقط شناسه فایل می‌گیرم.

مسیر نهایی باید بررسی شود تا حمله Path Traversal اتفاق نیفتد.

احراز هویت، بررسی دسترسی، محدودیت حجم و ارسال فایل به صورت stream هم لازم است.

8. انتقال اطلاعات باید فقط با HTTPS انجام شود و اطلاعات حساس داخل URL نباشد.

احراز هویت، سطح دسترسی، اعتبارسنجی ورودی و rate limit باید فعال باشد.

رمز عبور و توکن نباید در لاگ ثبت شوند و secretها هم باید امن نگهداری شوند.

9. برای این کار از OpenAPI و Swagger استفاده می‌کنم.

با ابزارهایی مثل swagger-jsdoc مستندات از روی کد یا annotation ساخته می‌شود.

مزیتش اینه که مستندات قابل تست هستند و برای تیم فرانت و بک قابل فهم‌تر می‌باشند.


10. تست‌های غیرعملکردی فقط درست بودن قابلیت را بررسی نمی‌کنند، بلکه کیفیت اجرای آن را هم می‌سنجند.

مواردی مثل سرعت، امنیت، پایداری، مقیاس‌پذیری و مصرف منابع را شامل می‌شوند.

با این تست‌ها مشکلاتی که در تست معمولی معلوم نیست پیدا می‌شوند.

11. مثلاً برای endpoint جست‌وجوی محصول، ۵۰۰ کاربر همزمان را به مدت ۱۰ دقیقه شبیه سازی می‌کنم.

با k6 زمان پاسخ، تعداد درخواست و درصد خطا را اندازه می‌گیرم.

معیار قبولی می‌تواند response time کمتر از ۵۰۰ میلی‌ثانیه و خطای زیر یک درصد باشد.

12. باید ورود و سطح دسترسی، اعتبارسنجی ورودی و حمله‌هایی مثل SQL Injection و XSS تست شوند.

همچنین dependencyها را با npm audit یا Snyk بررسی می‌کنم.

برای بخش‌های حساس، اسکن DAST و تست نفوذ دستی هم انجام می‌شود.

13. وقتی سرویس باید مدت طولانی بدون restart کار کند، تست پایداری لازم می‌شود.

این موضوع برای سرویس‌های پرترافیک و سامانه‌های ۲۴ ساعته خیلی مهم است.

در تست، memory leak، افزایش مصرف CPU و افت تدریجی سرعت بررسی می‌شود.

14. تعداد کاربران یا درخواست‌ها را کم کم زیاد می‌کنم و رفتار سیستم را اندازه می‌گیرم.

CPU، حافظه، زمان پاسخ، خطاها و ظرفیت دیتابیس بررسی می‌شوند.

هدف این است که بفهمیم سیستم تا چه حد با افزایش منابع یا instanceها جواب می‌دهد.

15. با mock یا ابزارهایی مثل Toxiproxy قطعی، تاخیر، timeout و خطای سرویس وابسته را شبیه‌سازی می‌کنم.

بعد بررسی می‌کنم retry، fallback و circuit breaker درست کار می‌کنند یا نه.

نباید خرابی یک سرویس باعث خوابیدن کل سیستم شود.

16. تست امنیتی شامل بررسی کلی کد، تنظیمات، dependencyها و کنترل‌های امنیتی است.

تست نفوذ شبیه حمله واقعی است و معمولاً توسط متخصص امنیت انجام می‌شود.

در تست نفوذ تلاش می‌شود آسیب‌پذیری واقعاً پیدا و میزان اثرش مشخص شود.

17. تست‌های غیرعملکردی نباید فقط آخر پروژه انجام شوند.

تست‌های پایه امنیت و کارایی بهتر است از اول در CI اجرا شوند.

قبل از انتشار و بعد از تغییرات بزرگ معماری هم تست کامل‌تری انجام می‌دهم.


18. ISTQB برای برنامه‌ریزی و اجرای تست یک چارچوب و زبان مشترک می‌دهد.

کمک می‌کند نیازمندی‌ها، ریسک‌ها و معیار قبولی منظم بررسی شوند.

در نتیجه تست فقط به پیدا کردن باگ در آخر کار محدود نمی‌شود.

19. در Black Box فقط رفتار بیرونی سیستم را بررسی می‌کنیم و کاری به کد داخلی نداریم.

در White Box ساختار کد، branchها و مسیرهای داخلی هم بررسی می‌شوند.

مثلاً تست API از بیرون Black Box است، ولی بررسی code coverage بیشتر White Box حساب می‌شود.

20. هدف Regression این است که مطمئن شویم تغییر جدید قابلیت‌های قبلی را خراب نکرده.

بعد از اصلاح باگ، تغییر API یا به‌روزرسانی پکیج‌ها باید تست‌های قبلی دوباره اجرا شوند.

اجرای خودکار آن‌ها در CI خیلی کمک می‌کند.

21. تست Acceptance وقتی انجام می‌شود که feature از نظر فنی آماده شده و باید با نیاز کسب‌وکار مقایسه شود.

این تست معمولاً قبل از انتشار نسخه انجام می‌شود.

سناریوها باید بر اساس رفتار واقعی کاربر و معیارهای پذیرش باشند.

22. تستر فقط دنبال باگ نیست؛ ریسک‌ها و ابهام‌های نیازمندی را هم بررسی می‌کند.

تست‌ها را طراحی و اجرا کرده و نتیجه را واضح به تیم گزارش می‌دهد.

همچنین با توسعه‌دهنده و مالک محصول برای بهتر شدن کیفیت همکاری دارد.

23. اول بخش‌های حساس مثل پرداخت، ورود، مجوزها و APIهای عمومی را مشخص می‌کنم.

برای هر ریسک احتمال و میزان خسارت را در نظر می‌گیرم.

موارد پرریسک باید زودتر و با تست بیشتری بررسی شوند.

24. تست Exploratory یعنی تستر همزمان با شناخت سیستم، مسیرهای مختلف را امتحان کند.

برای پیدا کردن رفتارهای عجیب، خطاهای مرزی و مشکلاتی که در سناریوها نیستند مفید است.

نتیجه تست باید ثبت شود تا بعداً قابل پیگیری باشد.


25. در BDD، بخش Given وضعیت اولیه را مشخص می‌کند.

When عملی است که کاربر یا سیستم انجام می‌دهد و Then نتیجه مورد انتظار را می‌گوید.

این مدل باعث می‌شود سناریو برای فنی و غیر فنی قابل فهم باشد.

26. اول سناریوها را در فایل‌های feature با زبان Gherkin می‌نویسیم.

بعد برای Given، When و Then در step definition کد JavaScript یا TypeScript می‌نویسیم.

در آخر Cucumber را از طریق npm script اجرا و گزارش می‌گیریم.

27. وقتی تیم فنی و کسب‌وکار تعامل زیادی دارند، BDD انتخاب خوبی است.

برای قابلیت‌هایی که رفتار کاربر در آن‌ها مهم است هم کاربرد دارد.

TDD بیشتر روی طراحی و تست کد تمرکز دارد، اما BDD رفتار قابل مشاهده سیستم را می‌سنجد.

28. فایل‌های feature را به step definition وصل می‌کنیم و برای هر مرحله کد اجرایی می‌نویسیم.

بعد دستور Cucumber را داخل package.json قرار می‌دهیم.

در CI هم با اجرای همان دستور، سناریوها خودکار تست می‌شوند.

29. سناریوهای API به زبان ساده نوشته می‌شوند و برای همه اعضای تیم قابل فهم هستند.

قبل از پیاده سازی، رفتار endpoint و نتیجه مورد انتظار مشخص می‌شود.

هم تست داریم و هم یک جور مستندات قابل استفاده برای API.

30. در پروژه‌های بزرگ، تعداد سناریوها زیاد و نگهداری آن‌ها سخت می‌شود.

گاهی stepهای تکراری و featureهای قدیمی باعث شلوغی و کندی تست می‌شوند.

باید سناریوها کوتاه، مرتب و تا جای ممکن قابل استفاده مجدد باشند.


31. معمولاً از fixture، فایل JSON، دیتابیس تست و factory برای ساخت داده استفاده می‌شود.

برای سرویس‌های خارجی هم mock server یا stub کاربرد دارد.

انتخاب روش به نوع تست و مقدار شباهت به محیط واقعی بستگی دارد.

32. با ابزارهایی مثل Faker اطلاعات ساختگی مثل نام و ایمیل تولید می‌کنم.

برای دیتابیس هم seed یا factory می‌نویسم تا داده‌ها قبل از تست ساخته شوند.

بهتر است داده‌ها قابل تکرار و مستقل از تست‌های دیگر باشند.

33. تا جای ممکن از داده واقعی استفاده نمی‌کنم و داده‌ها را ناشناس یا mask می‌کنم.

رمزها و کلیدها نباید داخل کد یا Git قرار بگیرند.

دسترسی به محیط تست باید محدود باشد و داده‌ها بعد از کار پاک شوند.

34. Stub معمولاً یک پاسخ از قبل تعیین شده برمی‌گرداند تا یک حالت خاص را تست کنیم.

Mock علاوه بر پاسخ، بررسی می‌کند تابع چند بار و با چه پارامتری صدا زده شده.

پس Stub بیشتر روی نتیجه تمرکز دارد و Mock روی نحوه تعامل.

35. می‌توان برای هر تست transaction ساخت و در پایان آن را rollback کرد.

روش دیگر استفاده از afterEach یا afterAll برای حذف اطلاعات تست است.

پاک سازی باید حتی وقتی تست fail شد هم انجام بشود.


36. برای تست رابط کاربری معمولاً از Playwright یا Cypress استفاده می‌کنم.

برای کامپوننت‌ها هم Jest و Testing Library مناسب هستند.

تست باید کارهایی مثل کلیک، وارد کردن اطلاعات و دیدن پیام خطا را شبیه سازی کند.

37. در CI ابتدا برنامه را بالا می‌آوریم و dependencyها را نصب می‌کنیم.

بعد مرورگرها نصب شده و تست‌های Playwright یا Cypress در حالت headless اجرا می‌شوند.

در صورت خطا، screenshot و trace ذخیره می‌کنیم تا مشکل معلوم شود.

38. تست Functional بررسی می‌کند قابلیت واقعاً کار می‌کند؛ مثلاً دکمه عملیات درستی انجام می‌دهد.

تست Visual ظاهر، رنگ، فاصله و چیدمان صفحه را با نمونه مورد انتظار مقایسه می‌کند.

ممکن است عملکرد درست باشد ولی ظاهر صفحه خراب شده باشد.

39. صفحه‌های داینامیک به خاطر درخواست‌های async، انیمیشن و تغییر محتوا تست‌های ناپایدار ایجاد می‌کنند.

باید از selectorهای ثابت و انتظارهای هوشمند استفاده کرد.

استفاده زیاد از sleep معمولاً مشکل را بدتر می‌کند.

40. با ابزارهایی مثل axe و Lighthouse مشکلات رایج accessibility را پیدا می‌کنم.

label فرم‌ها، کنتراست، حرکت با کیبورد و ترتیب focus هم باید بررسی شوند.

چند تست دستی با صفحه‌خوان هم لازمه، چون ابزارها همه مشکلات را پیدا نمی‌کنند.


41. زمان، سطح لاگ، نام سرویس، endpoint، status code و زمان پاسخ باید ثبت شوند.

برای خطا هم stack trace و شناسه درخواست مفید است.

رمز عبور، توکن و اطلاعات بانکی نباید داخل لاگ نوشته شوند.

42. اطلاعات حساس را قبل از ثبت mask یا حذف می‌کنم.

دسترسی به لاگ‌ها باید محدود باشد و انتقال و ذخیره آن‌ها بهتر است رمزنگاری شود.

مدت نگهداری و امکان بررسی تغییرات لاگ هم باید مشخص باشد.

43. برای خود Node.js ابزارهایی مثل Pino و Winston گزینه‌های خوبی هستند.

برای جمع آوری و جست‌وجوی مرکزی می‌توان از ELK، Grafana Loki یا Datadog استفاده کرد.

انتخاب نهایی به حجم لاگ و امکانات مورد نیاز پروژه بستگی دارد.


44. ارتباطات را با integration test و درخواست‌های شبیه سازی شده با mock تست می‌کنم.

ابزارهایی مثل Supertest، Nock، Postman و Newman در این کار کاربرد دارند.

در تست کامل‌تر، TLS، proxy، DNS و ارتباط بین سرویس‌ها هم بررسی می‌شوند.

45. با ابزارهایی مثل Toxiproxy تاخیر، قطع ارتباط و packet loss ایجاد می‌کنم.

بعد بررسی می‌کنم timeout، retry و fallback درست اجرا می‌شوند یا نه.

هدف اینه که خرابی شبکه باعث هنگ کردن کل سرویس نشود.

46. برای هر درخواست باید timeout مشخص و منطقی تعریف شود.

Retry باید محدود باشد و با فاصله زمانی بیشتر انجام شود؛ وگرنه فشار روی سرویس زیاد می‌شود.

همچنین درخواست‌های لغو شده باید connection و منابع را آزاد کنند.


47. برای هر feature یا تغییر مربوط به تست، یک branch جدا می‌سازم.

تغییرات از طریق Pull Request بررسی می‌شوند و CI قبل از merge تست‌ها را اجرا می‌کند.

branchهای کوتاه و commitهای کوچک مدیریت را راحت‌تر می‌کنند.

48. commitها را با پیام واضح ثبت می‌کنم و تغییر تست را همراه تغییر کد قرار می‌دهم.

با git log و git blame می‌شود فهمید یک تست چرا و توسط چه تغییری عوض شده.

برای تغییرات مهم هم توضیح آن در Pull Request نوشته می‌شود.

49. اول branch اصلی را به‌روز می‌کنم و فایل‌های دارای conflict را با دقت بررسی می‌کنم.

باید منطق هر دو تغییر را بفهمیم، نه اینکه کورکورانه یکی را نگه داریم.

بعد از حل مشکل، تست‌های همان بخش و کل تست‌های اصلی را اجرا می‌کنم.


50. تفاوت مدل دستگاه‌ها، نسخه سیستم عامل، اندازه صفحه و سرعت اینترنت تست موبایل را سخت می‌کند.

گاهی برنامه روی emulator درست است ولی روی گوشی واقعی مشکل دارد.

برای پوشش بهتر باید از device farm، چند دستگاه واقعی و تست شبکه ضعیف استفاده کرد.
