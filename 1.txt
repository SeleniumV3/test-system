1. در یک پروژه Node.js، چگونه می‌توان یک RESTful API طراحی کرد که قابلیت مقیاس‌پذیری داشته باشد؟

API را به شکل ماژولار و لایه‌ای طراحی می‌کنم؛ مثلاً جدا کردن Route، Controller، Service و Repository.

از Stateless بودن، کش، pagination، connection pooling و دیتابیس مناسب استفاده می‌کنم.

برای افزایش ظرفیت هم سرویس را با Docker و چند instance اجرا کرده و پشت Load Balancer قرار می‌دهم.

2. در Node.js برای مدیریت خطاهای API چه راهکارهایی وجود دارد که باعث افزایش امنیت و پایداری سرویس شود؟

یک middleware مرکزی برای مدیریت خطا قرار می‌دهم تا همه خطاها شکل یکسانی داشته باشند.

در محیط production جزئیات خطای داخلی را به کاربر نشان نمی‌دهم و فقط پیام مناسب برمی‌گردانم.

خطاها باید همراه با correlation ID لاگ شوند و خطاهای پیش‌بینی‌نشده هم باعث crash بی‌دلیل سرویس نشوند.

3. چگونه می‌توان صحت ورودی‌های دریافتی از کلاینت را در یک API بررسی کرد؟

ورودی‌ها را قبل از رسیدن به منطق اصلی با ابزارهایی مثل Joi، Zod یا express-validator بررسی می‌کنم.

نوع داده، اجباری بودن فیلدها، طول رشته و فرمت‌هایی مثل ایمیل باید کنترل شود.

همچنین باید ورودی‌ها در برابر SQL Injection، XSS و داده‌های غیرمنتظره پاک‌سازی یا محدود شوند.

4. اگر یک API کند اجرا می‌شود، چه ابزارها و روش‌هایی برای شناسایی و حل مشکل پیشنهاد می‌دهید؟

اول با لاگ، APM و ابزارهایی مثل Node.js Profiler یا Clinic.js مشخص می‌کنم زمان در کدام بخش مصرف می‌شود.

کوئری‌های دیتابیس، درخواست‌های خارجی، مصرف CPU و Memory را بررسی می‌کنم.

بعد با index، cache، بهینه‌سازی کد، pagination و اجرای موازی کارهای مستقل مشکل را کاهش می‌دهم.

5. در یک پروژه Node.js، چگونه می‌توانید API را در برابر حملات brute-force محافظت کنید؟

برای endpointهای ورود از rate limiting بر اساس IP، حساب کاربری یا ترکیبی از هر دو استفاده می‌کنم.

بعد از چند تلاش ناموفق، تأخیر تدریجی، قفل موقت حساب یا CAPTCHA اضافه می‌شود.

رمز عبور هم باید با bcrypt یا Argon2 هش شود و تلاش‌های مشکوک در لاگ ثبت شوند.

6. در چه شرایطی استفاده از GraphQL به جای REST در یک پروژه Node.js توصیه می‌شود؟

وقتی کلاینت‌های مختلف اطلاعات متفاوتی نیاز دارند و مشکل over-fetching یا under-fetching داریم، GraphQL مناسب است.

برای اپلیکیشن‌های پیچیده و چندمنبعی هم می‌تواند تجربه بهتری بدهد.

اما اگر API ساده، قابل cache و resource-based باشد، REST معمولاً انتخاب ساده‌تر و کم‌هزینه‌تری است.

7. چگونه می‌توان یک endpoint امن برای دانلود فایل در Node.js پیاده‌سازی کرد؟

مسیر فایل را مستقیماً از ورودی کاربر قبول نمی‌کنم و فقط یک شناسه یا نام مجاز دریافت می‌کنم.

مسیر نهایی باید با directory امن مقایسه شود تا حمله‌هایی مثل Path Traversal رخ ندهد.

احراز هویت، بررسی مجوز، محدودیت حجم، نوع فایل و ارسال به صورت stream هم ضروری است.

8. برای پیاده‌سازی یک API که اطلاعات حساس را منتقل می‌کند، چه نکات امنیتی باید رعایت شود؟

ارتباط فقط باید از طریق HTTPS انجام شود و توکن‌ها و اطلاعات حساس داخل URL قرار نگیرند.

احراز هویت، سطح دسترسی، اعتبارسنجی ورودی، rate limiting و مدیریت امن secretها لازم است.

اطلاعات حساس نباید در لاگ ثبت شوند و بهتر است داده‌های مهم در حالت ذخیره‌شده هم رمزنگاری شوند.

9. در صورت نیاز به مستندسازی خودکار API در Node.js، چه راهکاری پیشنهاد می‌دهید و چرا؟

استفاده از OpenAPI/Swagger را پیشنهاد می‌کنم؛ چون هم مستندات تولید می‌کند و هم امکان تست endpointها را می‌دهد.

در پروژه‌هایی مثل Express می‌توان از swagger-jsdoc و swagger-ui-express استفاده کرد.

مستندات باید کنار کد نگهداری و در CI بررسی شوند تا از API واقعی عقب نمانند.


10. در پروژه‌های Node.js، چرا تست‌های غیرعملکردی اهمیت دارند و چه مواردی را شامل می‌شوند؟

تست عملکردی می‌گوید سیستم درست کار می‌کند، اما تست غیرعملکردی می‌سنجد چقدر خوب و قابل اتکا کار می‌کند.

مواردی مثل Performance، Security، Stability، Scalability، Usability و Accessibility را شامل می‌شود.

این تست‌ها مشکلاتی را پیدا می‌کنند که معمولاً در تست‌های عادی دیده نمی‌شوند.

11. یک سناریوی تست کارایی برای یک سرویس Node.js بنویسید.

فرض می‌کنیم endpoint جست‌وجوی محصولات باید با ۵۰۰ کاربر هم‌زمان تست شود.

با ابزارهایی مثل k6 یا JMeter، درخواست‌ها را برای ۱۰ دقیقه ارسال می‌کنیم و response time، throughput و error rate را می‌سنجیم.

معیار قبولی مثلاً p95 کمتر از ۵۰۰ میلی‌ثانیه و خطای کمتر از یک درصد است.

12. برای اطمینان از امنیت یک سرویس Node.js چه تست‌هایی باید انجام شود؟

اعتبارسنجی ورودی، احراز هویت، مجوزها، مدیریت session و حملاتی مثل Injection و XSS باید بررسی شوند.

همچنین dependencyها را با npm audit یا Snyk اسکن می‌کنم.

در مراحل بعدی تست DAST، بررسی تنظیمات سرور و تست دستی برای مسیرهای حساس انجام می‌شود.

13. در چه شرایطی تست پایداری برای یک سرویس اهمیت پیدا می‌کند؟

وقتی سرویس باید ساعت‌ها یا روزها بدون restart کار کند، تست پایداری اهمیت زیادی دارد.

برای سرویس‌های پرترافیک، مالی، مانیتورینگ و سامانه‌های ۲۴ ساعته این تست ضروری است.

در این تست memory leak، رشد مصرف CPU، قطع شدن connection و افت تدریجی performance بررسی می‌شود.

14. چگونه می‌توان تست مقیاس‌پذیری را برای یک سیستم Node.js انجام داد؟

تعداد کاربران یا درخواست‌ها را مرحله‌به‌مرحله افزایش می‌دهم و رفتار سیستم را اندازه‌گیری می‌کنم.

هم‌زمان CPU، Memory، زمان پاسخ، تعداد خطا و ظرفیت دیتابیس بررسی می‌شود.

تست باید مشخص کند سیستم با scale-up یا scale-out تا چه ظرفیتی پاسخ قابل قبول می‌دهد.

15. در تست‌های غیرعملکردی، چگونه می‌توان رفتار سیستم را در شرایط شکست سرویس‌های وابسته بررسی کرد؟

با mock یا ابزارهایی مثل Toxiproxy، قطع شدن سرویس، timeout، پاسخ کند و خطای ۵۰۰ را شبیه‌سازی می‌کنم.

بعد بررسی می‌کنم retry، timeout، circuit breaker و fallback درست کار می‌کنند یا نه.

مهم است شکست یک سرویس باعث از کار افتادن زنجیره‌ای کل سیستم نشود.

16. تفاوت تست امنیتی و تست نفوذ در پروژه‌های Node.js چیست؟

تست امنیتی مفهوم گسترده‌تری دارد و شامل اسکن dependencyها، بررسی کد، تنظیمات و کنترل‌های امنیتی است.

تست نفوذ معمولاً شبیه‌سازی حمله واقعی توسط متخصص امنیت است.

در تست نفوذ تلاش می‌شود عملاً آسیب‌پذیری کشف و میزان اثر آن مشخص شود.

17. چه زمانی باید تست‌های غیرعملکردی را در فرآیند توسعه نرم‌افزار اجرا کرد؟

نباید همه این تست‌ها را فقط به آخر پروژه موکول کرد.

تست‌های امنیتی و performance پایه بهتر است از مراحل اولیه و در CI اجرا شوند.

قبل از انتشار نسخه و هنگام تغییرات بزرگ معماری هم باید تست‌های کامل‌تر انجام شوند.


18. در پروژه‌های Node.js، استانداردهای ISTQB چه کمکی به بهبود فرآیند تست می‌کند؟

ISTQB یک زبان مشترک و چارچوب مشخص برای برنامه‌ریزی و اجرای تست ارائه می‌دهد.

کمک می‌کند نیازمندی‌ها، ریسک‌ها، طراحی تست و معیار قبولی منظم‌تر بررسی شوند.

در نتیجه تست فقط به پیدا کردن باگ در آخر کار محدود نمی‌شود.

19. تفاوت تست Black Box و White Box در پروژه‌های Node.js چیست؟

در Black Box، تستر بدون دانستن ساختار داخلی، رفتار API یا برنامه را از بیرون بررسی می‌کند.

در White Box، کد، branchها، functionها و مسیرهای داخلی هم بررسی می‌شوند.

مثلاً تست endpoint با Postman معمولاً Black Box است، ولی بررسی coverage کد White Box محسوب می‌شود.

20. در چارچوب ISTQB، هدف از تست Regression در پروژه‌های Node.js چیست؟

هدف Regression این است که مطمئن شویم تغییر جدید قابلیت‌های قبلی را خراب نکرده است.

بعد از اصلاح باگ، تغییر dependency یا تغییر در API باید تست‌های مرتبط دوباره اجرا شوند.

اجرای خودکار این تست‌ها در CI کمک می‌کند خطاها زودتر مشخص شوند.

21. در پروژه‌های Node.js، چه زمانی تست Acceptance باید انجام شود؟

وقتی یک قابلیت از نظر تیم توسعه آماده است و می‌خواهیم مطمئن شویم نیاز کسب‌وکار را برآورده می‌کند.

این تست معمولاً نزدیک پایان یک feature یا قبل از انتشار انجام می‌شود.

معیارها باید از روی نیازمندی‌ها و سناریوهای واقعی کاربر تعریف شده باشند.

22. در استاندارد ISTQB، نقش تستر در پروژه‌های نرم‌افزاری چیست؟

تستر فقط دنبال باگ نیست؛ باید ریسک‌ها، ابهام‌های نیازمندی و کیفیت کلی محصول را بررسی کند.

او تست‌ها را طراحی و اجرا می‌کند و نتایج را به شکل قابل فهم گزارش می‌دهد.

تستر همچنین باید با تیم توسعه و محصول برای پیشگیری از خطا همکاری داشته باشد.

ابتدا بخش‌های حساس مثل پرداخت، احراز هویت، APIهای عمومی و عملیات‌های مهم را مشخص می‌کنم.

برای هر مورد احتمال وقوع و میزان اثر را می‌سنجم و موارد پرریسک را زودتر تست می‌کنم.

ریسک‌ها باید در طول پروژه بازبینی شوند، چون با تغییر سیستم ممکن است اولویتشان عوض شود.

24. در استاندارد ISTQB، تست Exploratory چه کاربردی در پروژه‌های Node.js دارد؟

در این روش تستر هم‌زمان با یادگیری سیستم، سناریوهای جدید را بررسی می‌کند و به مسیرهای از قبل نوشته‌نشده توجه دارد.

برای کشف رفتارهای غیرمنتظره، مشکلات usability و خطاهای مرزی مفید است.

بهتر است نتیجه و یافته‌ها ثبت شود تا قابل تکرار و پیگیری باشند.


25. در BDD، نقش سناریوی Given-When-Then در تست پروژه‌های Node.js چیست؟

Given وضعیت اولیه، When عملی که انجام می‌شود و Then نتیجه مورد انتظار را مشخص می‌کند.

این ساختار سناریو را برای توسعه‌دهنده، تستر و حتی مدیر محصول قابل فهم می‌کند.

در واقع نیازمندی کسب‌وکار را به تست قابل اجرا تبدیل می‌کند.

بعد برای عبارت‌های Given، When و Then در فایل‌های step definition کد JavaScript یا TypeScript قرار می‌دهیم.

وقتی تعامل بین تیم فنی و کسب‌وکار زیاد است و باید رفتار سیستم به زبان قابل فهم نوشته شود، BDD مناسب‌تر است.

برای APIها و قابلیت‌هایی که سناریوهای کاربری مشخص دارند هم کاربرد خوبی دارد.

TDD بیشتر روی طراحی و تست واحد کد تمرکز دارد، اما BDD روی رفتار قابل مشاهده سیستم تمرکز می‌کند.

سناریوها را با Cucumber یا ابزار مشابه به step definition متصل می‌کنیم.

سناریوها به شکل قابل فهم نوشته می‌شوند و رفتار API برای همه اعضای تیم روشن می‌ماند.

این روش باعث می‌شود معیار قبولی هر endpoint قبل از پیاده‌سازی مشخص باشد.

برای کنترل این مشکل باید سناریوها کوتاه، قابل استفاده مجدد و بر اساس رفتار واقعی کاربر باشند.

داده‌ها می‌توانند از fixtureها، فایل‌های JSON، دیتابیس تست یا factoryها تولید شوند.

برای سرویس‌های خارجی معمولاً از mock server یا stub استفاده می‌شود.

Mock علاوه بر شبیه‌سازی، بررسی می‌کند تابع یا سرویس با آرگومان و تعداد دفعات درست صدا زده شده است.

در عمل Stub روی نتیجه تمرکز دارد و Mock روی نحوه تعامل.

35. در پروژه‌های Node.js، چگونه می‌توان داده‌های تست را پس از اجرای تست پاک‌سازی کرد؟

راه دیگر اجرای تابع cleanup در hookهایی مثل afterEach یا afterAll است.

برای تست end-to-end رابط کاربری معمولاً از Playwright یا Cypress استفاده می‌شود.

برای تست کامپوننت‌ها هم ابزارهایی مثل Jest و Testing Library کاربرد دارند.

تست‌ها باید رفتار واقعی کاربر مثل کلیک، ورود اطلاعات و نمایش پیام خطا را بررسی کنند.

37. چگونه می‌توان تست‌های UI را در pipeline CI/CD پروژه Node.js اجرا کرد؟

در pipeline ابتدا dependencyها نصب و برنامه در محیط تست اجرا می‌شود.

بعد مرورگرهای موردنیاز Playwright یا Cypress نصب شده و تست‌ها در حالت headless اجرا می‌شوند.

در صورت خطا، screenshot، video و trace ذخیره می‌کنم تا عیب‌یابی راحت‌تر شود.

38. در تست‌های UI، چه تفاوتی بین تست Functional و Visual وجود دارد؟

تست Functional بررسی می‌کند قابلیت واقعاً کار می‌کند؛ مثلاً دکمه عملیات درست را انجام می‌دهد.

تست Visual ظاهر صفحه، فاصله‌ها، رنگ‌ها و چیدمان را با نمونه مورد انتظار مقایسه می‌کند.

ممکن است یک صفحه از نظر functional درست باشد ولی از نظر ظاهری مشکل داشته باشد.

39. در پروژه‌های Node.js، چه چالشی در تست UIهای داینامیک وجود دارد؟

تغییر محتوای صفحه، درخواست‌های async، انیمیشن و عناصر با زمان‌بندی متفاوت باعث flaky شدن تست می‌شوند.

استفاده از selectorهای پایدار، انتظار هوشمند و mock کردن درخواست‌های غیرضروری کمک می‌کند.

نباید فقط بر اساس موقعیت CSS یا زمان‌های ثابت مثل sleep تست بنویسیم.

40. در تست UI، چگونه می‌توان اطمینان حاصل کرد که همه عناصر قابل دسترس هستند؟

از ابزارهایی مثل axe-core، Lighthouse و تست‌های صفحه‌خوان استفاده می‌کنم.

مواردی مثل label فرم‌ها، کنتراست رنگ، navigation با کیبورد و ترتیب focus باید بررسی شوند.

تست خودکار کافی نیست و چند بررسی دستی با ابزارهای accessibility هم لازم است.


41. در پروژه‌های Node.js، چه اطلاعاتی باید در لاگ‌های سیستمی ثبت شود تا عیب‌یابی ساده‌تر شود؟

زمان، سطح لاگ، نام سرویس، endpoint، status code، مدت اجرای درخواست و correlation ID مفید هستند.

برای خطا باید stack trace، نوع خطا و context لازم ثبت شود.

اطلاعات حساس مثل رمز عبور، توکن و شماره کارت نباید وارد لاگ شوند.

42. چگونه می‌توان امنیت لاگ‌ها را در پروژه‌های Node.js تضمین کرد؟

قبل از ثبت لاگ، اطلاعات حساس را mask یا حذف می‌کنم و ورودی‌های کاربر را کنترل می‌کنم.

دسترسی به سیستم لاگ باید محدود و لاگ‌ها در زمان انتقال و ذخیره رمزنگاری شوند.

همچنین retention، audit و جلوگیری از دست‌کاری لاگ‌ها باید مشخص باشد.

43. چه ابزاری برای مدیریت و تحلیل لاگ‌های پروژه Node.js پیشنهاد می‌شود؟

برای خود برنامه‌هایی مثل Pino یا Winston مناسب هستند.

برای جمع‌آوری و تحلیل مرکزی می‌توان از ELK Stack، Grafana Loki یا سرویس‌هایی مثل Datadog استفاده کرد.

انتخاب ابزار به حجم لاگ، بودجه، نیاز به جست‌وجو و زیرساخت پروژه بستگی دارد.


44. در پروژه‌های Node.js، برای تست ارتباطات شبکه‌ای چه روش‌هایی وجود دارد؟

می‌توان درخواست‌های واقعی را با integration test و درخواست‌های شبیه‌سازی‌شده را با mock server تست کرد.

برای تست API ابزارهایی مثل Supertest، Postman/Newman و برای شبکه ابزارهایی مثل Nock کاربرد دارند.

در تست کامل‌تر، DNS، TLS، proxy و ارتباط سرویس‌ها هم بررسی می‌شوند.

45. چگونه می‌توان در تست‌های شبکه‌ای رفتار سیستم را در مواجهه با تاخیر یا قطعی بررسی کرد؟

با ابزارهایی مثل Toxiproxy یا قابلیت‌های شبیه‌سازی شبکه، latency، قطع ارتباط و packet loss ایجاد می‌کنم.

بعد بررسی می‌کنم timeout، retry، fallback و پیام خطا درست عمل می‌کنند یا نه.

هدف این است که قطعی موقت شبکه باعث هنگ کردن یا از کار افتادن کل سرویس نشود.

46. در پروژه‌های Node.js، چه نکاتی برای مدیریت timeout در ارتباطات شبکه‌ای باید رعایت شود؟

برای هر درخواست timeout مشخص و متناسب با نوع عملیات تعیین می‌کنم و مقدار نامحدود نمی‌گذارم.

Retry باید محدود، با backoff و فقط برای خطاهای قابل تکرار انجام شود.

همچنین باید درخواست‌های قبلی لغو شوند تا connection و resource بی‌دلیل مصرف نشود.


47. در پروژه‌های Node.js، چگونه می‌توان از Git برای مدیریت شاخه‌های توسعه تست استفاده کرد؟

برای هر feature یا تغییر تست یک branch جدا ایجاد می‌کنم و نام‌گذاری منظم انجام می‌دهم.

تغییرات از طریق Pull Request وارد شاخه اصلی می‌شوند و تست‌های CI قبل از merge اجرا می‌شوند.

شاخه‌های کوتاه‌عمر و commitهای کوچک، بررسی و برگشت تغییرات را ساده‌تر می‌کنند.

48. چگونه می‌توان تاریخچه تغییرات مرتبط با تست‌ها را در Git پیگیری کرد؟

commitها باید پیام واضح داشته باشند و تغییر کد و تست تا حد امکان کنار هم ثبت شود.

با دستورهایی مثل git log، git blame و جست‌وجوی commitها می‌توان دلیل تغییر تست را پیدا کرد.

برای تغییرات مهم هم بهتر است در Pull Request توضیح و لینک issue ثبت شود.

49. در صورت بروز تعارض در شاخه‌های تست، چه راهکاری پیشنهاد می‌دهید؟

ابتدا شاخه اصلی را به‌روز می‌کنم و فایل‌های دارای conflict را با دقت بررسی می‌کنم.

نباید صرفاً یکی از نسخه‌ها را انتخاب کرد؛ منطق تست و تغییرات هر دو شاخه باید فهمیده شود.

بعد از حل تعارض، تست‌های مرتبط و کل suite اصلی را اجرا کرده و نتیجه را در commit ثبت می‌کنم.


50. در پروژه‌های Node.js، چه چالش‌هایی در تست نرم‌افزارهای موبایل وجود دارد؟

تفاوت دستگاه‌ها، نسخه سیستم‌عامل، اندازه صفحه، سرعت شبکه و مجوزهای موبایل تست را سخت می‌کند.

همچنین تست روی دستگاه واقعی و emulator ممکن است نتایج متفاوتی داشته باشد.

برای پوشش بهتر باید از device farm، تست responsive، تست شبکه ضعیف و بررسی مصرف باتری و حافظه استفاده کرد.
